# AI / Agent / RAG 面试要点

> 全部对着自己项目里的代码讲，不背论文。

## 一、整体链路（一句话版）

浏览器发问 → 后端取最近 10 条历史 → 拼 system prompt（含工具说明）→ 发给模型 →
模型自回归生成，输出 `Thought` + `Action` → 后端解析 Action、执行工具 →
结果包成 `Observation` 塞回对话 → 再问模型 → 直到 `Finish[答案]` → 存库并流式推给前端。

代码：`routers/ai.py`（接口）→ `ai/agent.py`（循环）→ `ai/tools.py`（工具）→ `ai/rag.py`（检索）

## 二、RAG 是什么（我的理解）

**不是把整个库发给模型，也不是每次都强制检索。**

更像是工具调用：

> 用户问"雪崩怎么解决" → 模型自己决定调用 `search_knowledge("雪崩怎么解决")` →
> 后端在 `ai_chunks` 表里检索，挑出最相关的 4 段 → 包成 Observation 塞回对话 →
> 模型照着这 4 段回答，并注明出处。

**朴素 RAG**：每次请求都先检索一段内容再回答。
**工具式 RAG（我做的是这个）**：模型自己决定要不要查、用什么词查，可以多轮查。

好处：无关问题不查库；模型能把问题改写成更好的检索词。

## 三、关键数字（都能复述）

| 项 | 值 |
|---|---|
| 文章数 | 38 篇 |
| 切块数 | 2909 块 |
| 每块大小 | 约 400 字，相邻重叠 60 字 |
| 每次检索 | 取 Top-4（同篇文章只取一块，覆盖面更广） |
| 检索耗时 | 约 0.3 秒 |
| 评测 | 25 条问题：Top-1 命中 92%，Top-4 命中 100% |
| 单次对话 token | 约 2200（4 块 ≈1200 + 系统提示 ≈400 + 历史 ≈600） |

## 四、为什么切块要重叠

一句话可能正好被切在两块的交界处，两边都不完整、都搜不到。
每块开头重复上一块结尾 60 字，保证边界附近的内容至少有一块是完整的。代价是存储多约 15%。

## 五、为什么现在用关键词检索，不用向量

1. DeepSeek 没有 embedding 接口，接第三家要额外 key 和基建；
2. 站里只有 2909 块，全量扫描 0.3 秒，瓶颈不在这里；
3. **接口已按向量检索的形态设计**（输入问题 → 输出片段 + 出处），换实现不影响上层。

关键词检索的短板：字面不重合就搜不到（"怎么部署" vs "上线流程"）。
向量的优势是比"意思"，靠 embedding 把文字变成向量，比余弦相似度。

## 六、如果继续做，下一步是什么

1. **向量检索**：bge-m3 之类模型算 embedding，存向量列或独立向量库；
2. **混合检索**：关键词 + 向量各取一批，合并去重；
3. **rerank**：粗筛 50 条，再用更贵的模型精排前 10；
4. **新文章自动入索引**：现在切块是手动跑脚本，发布文章后要异步触发，否则 AI 搜不到新内容。

## 七、Agent 循环要点

- 模型只能"说"要调什么，**真正执行的是后端代码**（`TOOLS` 字典就是安全边界）；
- 工具结果必须伪装成 `user` 角色的 `Observation` 塞回对话，模型下一轮才看得到；
- **最大轮数 5**：防止原地打转，转满强制收口；
- 工具出错不抛异常给用户，把错误写成 Observation 让模型自己换策略；
- 提示词里的"输出格式"一旦被破坏（少个冒号），整个循环就断——这是提示词脆弱性。

## 八、可能被追问的点

**Q：模型真的执行函数了吗？**
没有。模型只输出一行文本 `Action: search_articles("Redis")`，后端用正则解析出工具名和参数，再从 `TOOLS` 字典里取出函数执行。

**Q：怎么防死循环？**
最大轮数 + 提示词里明确"信息够了就输出 Finish"。

**Q：多轮对话怎么存？**
`ai_conversations`（会话）+ `ai_messages`（消息）两张表，一对多；每次只取最近 10 条拼进 prompt，防止上下文爆掉。

**Q：流式怎么实现？**
后端把模型输出转成 SSE（`text/event-stream`），前端用 fetch 读 `res.body`，按 `\n\n` 切事件逐段渲染。不能用 EventSource（只能 GET、不能带请求头），也不能用 axios（会等整个响应收完）。
